## What changed

- `sync()` replaces `push()` and `pullOrSeed()`: read the row (`data, updated_at`), reconcile key by key, write
  back only if the cloud copy changed, apply merged values locally only for keys the page has not changed since
  they were read. `StudyHubAccount.push` stays as an alias.
- **Per-key rule (three-way).** Each browser keeps `levlprep_sync_v1` = `{ uid, at, fails, base }`, where `base`
  is a hash of each key's value at its last sync. For a key: same on both sides, keep; only one side has it, keep
  it unless the other side deleted it since the last sync (deletions propagate); only the cloud changed, take the
  cloud; only this browser changed, take local (so un-flags and resets propagate) unless a sync rewrote that key
  under the open page this session, in which case merge (a page holding state in memory writes a stale copy back,
  and merging stops it erasing the other device's work); both changed or first sync on this device, merge.
  Merge = the key's registered merger, else structural: numbers max, booleans OR, arrays union, date strings
  later, objects with a stamp field (`t`, `ts`, `updatedAt`, `day`...) newer wins whole, other objects key by key;
  leftovers (settings, in-progress exam) are a conflict: local wins, except on a device's first sync where the
  account wins (the old behaviour).
- **Reused progress-backup.js's merge.** The structural rules moved from `progress-backup.js` into `account.js`
  (`StudyHubAccount.mergeRaw`); `progress-backup.js` now delegates, so restore and sync cannot drift. Every page
  that offers a restore loads account.js; without it a restore keeps one side per key and never deletes.
- **Optimistic concurrency.** Write = `update ... eq('id') eq('updated_at', <read value>) select('updated_at')`
  (`is null` for a legacy null stamp), or `insert` when there was no row (duplicate key 23505 = conflict). Zero
  rows back = another device wrote first: re-read, re-merge, retry, at most 4 attempts, then counted as a
  failure. The new stamp is always later than the one read even when the device clock is behind. Single-flight:
  a sync called while one runs queues one more.
- **When it runs.** Every signed-in page load, tab focus / `visibilitychange` to visible (throttled 20 s), the
  30 s timer, 1.5 s after `syncSoon()`, and on hide/pagehide. Keys a sync writes into the page fire a `storage`
  event (pages that already listen re-render) and `levlprep:synced`. If the load-time sync brings something in
  before the user has clicked or typed, the page reloads once per tab session (same guard key as the old
  sign-in reload); after sign-in it reloads once as before.
- **Sign out** now refuses to drop unsynced work silently: if the final sync fails, the menu says so and a second
  click signs out anyway.
- `theme.css`: one rule for the failing ring (`.account-btn[data-sync="error"]`), smallest edit in a shared file.

## Guards

  shared by two simulated devices: interleaved syncs keep both devices' progress; keys/namespaces another page
  registered survive; a write that misses re-reads and retries (and is bounded at 4); deletions and un-flags
  propagate; a stale in-memory write-back cannot erase the other device's work; a page write that lands while a

## Decisions and open items

- **Weight:** site shell budget 249 -> 253 KB (measured 252.0 KB). The sync code is about +3.8 KB gzipped net of
  the 0.8 KB that left progress-backup.js. It has to be on every page because every page syncs. Comments were
  kept short; no other file's prose was cut to make room.
- **XP earned on two devices between syncs is max'd, not summed** (e.g. +50 on the phone and +30 on the laptop
  from 100 gives 150, not 180). Summing needs per-device counters in `hub_xp_v1`; deferred (hub-progress.js
  format change, out of scope).
- **Union resurrects within-value deletions only when both devices changed the same key** between syncs (an
  un-flag on one and a new flag on the other). One-sided edits propagate.
- Every signed-in page load now does one read of the row (writes only when something changed); before, a read
  happened every 30 s plus a write every 30 s regardless.
